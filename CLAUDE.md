# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This repository is an npm workspace (the `mcp-abap-adt-interfaces` layout) with two packages: `packages/auth-broker` — `@mcp-abap-adt/auth-broker` (4.1.0), a per-destination credential broker for SAP BTP/ABAP systems — and `packages/auth-broker-cli` — `@mcp-abap-adt/auth-broker-cli` (2.1.0), the `mcp-auth` and `mcp-sso` commands. For a destination name it builds the `IAuthProvider` the destination states (`getProvider`) from the means in its key store and the secret in its session store, and serves the token API (`getToken`, `refreshToken`, `createTokenRefresher`) on that same provider — or on an injected `IRefreshableTokenProvider` / factory, as in 3.x — writing what is obtained back as the session secret alone. Token lifecycle decisions are the provider's (`@mcp-abap-adt/auth-providers`); storage is the stores' (`@mcp-abap-adt/auth-stores`). The commands moved out of the library into the CLI package; up to 3.0.4 they shipped in the library. XSUAA and ABAP authentication types are both supported.

## Build and Development Commands

Everything runs from the repository root; the dev dependencies (Biome, TypeScript, Jest, ts-jest, semver) are the root's.

```bash
npm run build        # clean, Biome at error level, tsc -b over both packages
npm run test:check   # type-check both packages, tests included
npm run lint         # Biome with --write over packages/ and tools/
npm run lint:check   # Biome, read-only
npm run format
npm test             # Jest in every workspace
npm run check        # build, test:check, lint:check, check:graph, check:packed, check:publish (no Jest)
npm run test:stand   # the library's stand suites against UAA and Keycloak in Docker (needs Docker)
npm run test:live:x509  # an x509 XSUAA key against a real BTP subaccount (cf login; XSUAA_CF_API/ORG/SPACE)

# One package, one file, one case
npm test -w @mcp-abap-adt/auth-broker
npm test -w @mcp-abap-adt/auth-broker -- AuthBroker.test.ts -t "name of the case"
npm test -w @mcp-abap-adt/auth-broker-cli
```

- `check:graph` (`tools/check-graph.js`): runtime files (src outside `__tests__`) import only their package's allowlist, declare it in `dependencies`, and use every dependency; tests import only what the package declares (dependencies or devDependencies). The library never imports `auth-stores`.
- `check:packed` (`tools/check-packed.js`): the bin smoke check — pack both, install the tarballs into an empty directory, run `mcp-auth`/`mcp-sso` with `--version` (must print the CLI's version) and `help`, load the library (no `bin`). Needs the network.
- `check:publish` (`tools/test-publish-changed.js`): the release tool against fixture repositories.
- `release:publish` (`tools/publish-changed.js`): publishes exactly the versions the registry lacks, in workspace order, after one `npm run check`; refuses an untagged version. Tags are `<dir>-v<version>` (`auth-broker-v…`, `auth-broker-cli-v…`); the `v*` tags are the single package's history. Between a version bump and its tags it refuses for the whole repository: tag the merge commit first. Never `npm publish` a workspace by hand.

## Architecture

### Core Components

**AuthBroker** (`packages/auth-broker/src/AuthBroker.ts`) - The main class that orchestrates token management:
- Coordinates between session stores, service key stores, and token providers
- Asks a provider for a token and leaves the lifecycle (cached → refresh → login) to it
- Creates `ITokenRefresher` instances for dependency injection into consuming services (`createTokenRefresher`, unchanged since 3.x)
- `getProvider(destination)` builds the `IAuthProvider` the destination states (`authType`, and `grantType` for `jwt`/`saml`) from the service key store's means and the session store's secret — never one from the other's fields, never inferred from which fields are present. Every pair is built (`src/destinations.ts`): `basic`, `snc`, `jwt`/`none`, `saml`/`none`, the UAA grants `jwt`/`authorization_code`, `client_credentials`, `passcode`, the OIDC grants `jwt`/`oidc_authorization_code`, `device_code`, `password`, `token_exchange`, and the SAML grants `saml`/`saml2_pure`, `saml2_bearer` (the validator composed by the broker from the destination's trust and the consumer's replay store) — the client from the key store's `getAuthorizationConfig`, the seed from `loadSession`, each collaborator option (`authorization(destination, grant)`, `oidcAuthorization`, `deviceCodePresenter`, `samlCookies`, `assertionReplayStore`) called once per build and never disposed; no row requires `serviceUrl` and no provider is given it — the resource URL is the connector's, not authorization data; the broker reads it, with `sapClient`, only for the binding below; a destination lacking what its type needs is `DestinationConfigError` (`src/DestinationConfigError.ts`: names, never values). The build's promise is cached per destination, set before the first read, dropped on a throw
- **A stored secret is used only where it is bound** (`src/binding.ts`): the session keeps `issuedFor` (the resource: `serviceUrl` + `sap-client`) and `issuedBy` (`uaaUrl` + `client_id`; for `none` rows also `oidcIssuerUrl` or `samlAcsUrl`) beside the secret. One canonicalising function, the broker's only — scheme/host lower-cased by `URL`, port explicit (443/80), path without trailing `/`, one parameter re-encoded through `URLSearchParams` (`sap-client`, the means' `sapClient` first; `client_id`; none for an ACS), nothing else — applied to both sides. The rows that obtain a secret (UAA, OIDC, SAML) seed only when both match; otherwise the secret (refresh token included) is dropped, a fresh login follows, and one warn line names the destination only (`secret bound to another resource, discarded`). The `none` rows throw `DestinationConfigError` naming `issuedFor` (always compared) or `issuedBy` (compared only when the means state an issuer). Legacy files: auth-stores 3.1.0 composes the binding from `SAP_URL`/`SAP_CLIENT` and `SAP_UAA_URL`/`SAP_UAA_CLIENT_ID`, percent-encoded — the canonicaliser makes that compare equal
- Every token provider `getProvider` builds gets `onTokens`: one `saveSession` of the secret alone (`authorizationToken`, `expiresAt` fixed when the result arrives, `refreshToken` — the stored one carried forward only when the stored session is bound here) with `issuedFor` / `issuedBy` (each left out when the means lack its source), never a means field, nothing for a destination the key store states as `basic`/`snc`. It never throws: a failed write stays pending per destination in `src/SessionWriter.ts`, retried on an `unref()`ed timer (1 s doubling to 60 s), the latest result replacing a pending one, attempts per destination chained (never overlapping), failures logged by class name; `flush()` gives each one more attempt and rejects (`AggregateError`) naming the destinations still failing. Each write records its failure in a `WeakMap<ITokenResult, …>` keyed on the result the provider handed to `onTokens` (which `BaseTokenProvider` also returns), never the copy it writes, then on the destination (`Map<destination, …>`: one result object can be answered for several destinations, and only a landed write for the same destination clears it); the token API throws that recorded failure to its caller
- **Client authentication** (`src/clientAuthentication.ts`, 4.1.0): `AuthBrokerConfig.clientAuthentication` — a `ClientAuthenticationStrategy` `(context) => Promise<IClientAuthentication>`, the consumer's statement of how a client authenticates; no default, nothing inferred from a key. Called once per build for every row whose client authenticates (the UAA and OIDC grants, `saml2_bearer`; never `saml2_pure`, `none`, `basic`, `snc`) with `{ destination, grant, client (the key store's secret client through `contextClient`'s allowlist — `uaaUrl`, `uaaClientId`, `uaaClientSecret`, never a refresh token — or null), readCertificate() }` — `readCertificate` lazy and memoised over `IServiceKeyStore.getClientCertificate?` (interfaces-auth-broker 1.2.0). Its answer goes to the provider as `clientAuthentication` with no `clientSecret`; the row's client is the identity (`clientIdentity`: the secret client's `uaaUrl`/`uaaClientId`, else the certificate client's — never PEM). `resolveClientAuthentication` is the guard: any throw, and an answer without `authenticate`, becomes `DestinationConfigError(['clientAuthentication'])` in fixed words chosen by `instanceof` and `===` flags only (no message, no `cause`). Shipped factories, each failing closed: `fromServiceKeyCertificate()` (auth-providers' `tlsClientCertificate`, `<certUrl>/oauth/token`, `tlsMaterial()` awaited so bad PEM is refused at build) and `fromServiceKeySecret({ encoding: 'raw' | 'form' })` (`clientSecretBasic`; encoding required). A fallback is the consumer's composition. **Without a strategy: byte-for-byte 4.0.0**, nothing certificate-related called; a client row with no client id adds the hint `a certificate client needs a clientAuthentication strategy`. **The strategy path's binding** (`strategyBinding`): `issuedBy` from the identity (same client id → same session, whichever way it authenticates), and `unstatedResourceMatches` — a resource neither the means (no or unparseable `serviceUrl`) nor the session states matches; one-sided absence never does. The broker's three certificate phrases (`incomplete` / `expired` / `could not be used`) are its own copy, classified by auth-providers' exported `CertificateMaterialError` flags
- **The token API**: it first reads the key store's `authType` and refuses `basic`/`snc` (`DestinationConfigError`, `authType`) before any provider is asked. Without a `provider` option it takes `getProvider`'s provider from the same `built` cache (one token, one renewal per destination; a `none` destination → `DestinationConfigError` naming `provider`) and writes nothing itself. With one it keeps 3.x's reads (session, then key store; the factory promise-cached in `consumerBuilt`) and submits every answer, cache hits included, to the same `SessionWriter` — the secret alone, the stored refresh token carried whatever its binding (`carry: 'any'`), `issuedFor` from the URL + SAP client and `issuedBy` from a factory's client (none for an instance, `consumerBinding`), both fixed when the destination's consumer provider is built (an instance: at its first call for the destination) and cached with it — a later change of URL or client never re-labels what that provider obtained; a new broker picks the change up. **With a `clientAuthentication` strategy and a factory** (`consumerClientAuthentication`): the destination must state `jwt`/`saml` and a grant (else `DestinationConfigError(['authType','grantType'])`); for a client-authenticating grant the strategy is resolved first and the factory gets a fourth argument, `TokenProviderClient` (`clientAuthentication`, `uaaUrl`/`clientId` of the identity, `refreshToken` only when bound); the binding is `strategyBinding(consumerBinding(…, identity))`, every stored secret (refresh token in `authConfig` and the fourth argument; token/cookies/expiry in `connConfig`) passes only when `boundHere`, `carry: 'bound'`; a throwing factory is `DestinationConfigError(['provider','clientAuthentication'])`. An instance `provider` never gets the strategy. The 3.x `persist` (`setConnectionConfig` with `serviceUrl`/`authType`, `setAuthorizationConfig`) is gone

**Stores** (interfaces from `@mcp-abap-adt/interfaces-auth-broker`, implementations in `@mcp-abap-adt/auth-stores` — which the library's runtime never imports; only its tests and the CLI do):
- `IServiceKeyStore` - the means: `authType`, `grantType`, the client, user and password, the SNC/OIDC/SAML fields, `serviceUrl` (auth-stores: `EnvDestinationStore`, `AbapServiceKeyStore` / `XsuaaServiceKeyStore` with a `grantType` option); optionally `getClientCertificate` (interfaces-auth-broker 1.2.0; auth-stores 3.3.0: an x509 XSUAA key, or `EnvDestinationStore`'s `SAP_UAA_CLIENT_CERT_PATH` / `_KEY_PATH` / `SAP_UAA_CERT_URL`, `XSUAA_UAA_*` — an x509 client answers `getAuthorizationConfig` with `null`), read only on the strategy path. Read-only for the broker
- `ISessionStore` - the secret: token or cookies, `expiresAt`, refresh token, `issuedFor` / `issuedBy` (auth-stores 3: `AbapSessionStore`, `XsuaaSessionStore`, `EnvFileSessionStore`, the in-memory `Safe*`). auth-stores 1.x/2.x are not supported: they refuse a write of the secret alone

**Token Providers** (from `@mcp-abap-adt/auth-providers`):
- `getProvider` constructs them by name (`src/destinations.ts`): `BasicAuthProvider`, `SncLogonProvider`, `TokenAuthProvider`, `SamlAuthProvider`, `AuthorizationCodeProvider`, `ClientCredentialsProvider`, `UaaPasscodeProvider`, the four OIDC providers, `Saml2PureProvider`, `Saml2BearerProvider`; none is re-exported
- The token API with a consumer `provider` takes any `IRefreshableTokenProvider`

### Package Dependencies

The contracts come from the packages that declare them — `@mcp-abap-adt/interfaces-auth` 3.2 (tokens, `IClientAuthentication`, `STORE_ERROR_CODES`), `-auth-broker` 1.2 (the store contracts: `IConfig`, `IConnectionConfig`, `ISessionStore`, `IServiceKeyStore`, `IClientCertificate`), `-auth-sap` 2 (`IAuthorizationConfig`, `AuthType` — the only two that stayed there) and `-utils` (`ILogger`). The library depends on `auth-providers` 5.3 at runtime (`getProvider` constructs its classes; `tlsClientCertificate`, `clientSecretBasic`, `CertificateMaterialError`); the library's tests run on `auth-stores` 3.3 (a dev dependency). The CLI uses `auth-stores` 3.3 at runtime: its commands write a destination's means through `EnvDestinationStore.setDestination` and the secret only through the broker. npm installs a copy of `auth-stores` and `auth-providers` under each package's `node_modules`, so a class from one package's copy is not `instanceof` the other's — the CLI's tests identify an `AssertionValidationError` by name. **Not `@mcp-abap-adt/interfaces`**: that facade is deleted as of its 52.0.0, npm serves 51.0.0 to whoever is pinned to it, and nothing further ships there. Some of those types are re-exported here for convenience, each from the package that declares it. Store and provider implementations are in separate packages:
- `@mcp-abap-adt/auth-stores` - ABAP and XSUAA store implementations
- `@mcp-abap-adt/auth-providers` - Token provider implementations

### CLI Tool

`packages/auth-broker-cli/src/` — `mcp-auth.ts`, `mcp-sso.ts` (the bins, compiled to `dist/`: argument parsing, help, then `runMcpAuth` / `runMcpSso`), `runMcpAuth.ts`, `runMcpSso.ts` (what a run does, importable by tests: each takes its work directory and its collaborators explicitly), `destination.ts` (the two stores over one `<destination>.env`, `completeMeans`, `flushed`, the output copy and JSON), `mcpSsoConfig.ts` (the row a run states — `ssoRow`, `buildDestinationMeans` — and `buildCollaborators`), `samlMetadata.ts`, `workDir.ts`, `clientAuthentication.ts` (the `--client-auth certificate|secret`, `--basic-encoding`, `--cert-path`, `--key-path` flags shared by `mcp-auth` and `generate-env`: checked before anything is read or written, paths resolved to absolute, turned into the broker's strategy; `carriesCertificate` / `serviceKeyStoreFor` — a key carrying a `certificate` or `key` is never copied and is read by `XsuaaServiceKeyStore`), `jsonFile.ts` (a JSON file the user names, refused in fixed words — the parser's message quotes key bytes), and `generate-env-from-service-key.ts` with `generateEnv.ts` (a development script run with `tsx`, `npm run generate-env -w @mcp-abap-adt/auth-broker-cli -- … --grant <grant>`, not compiled). They import `AuthBroker` from `@mcp-abap-adt/auth-broker` by name, never by a path into its `dist`, and `--version` reads the CLI's own manifest.

Each command writes the destination's means first, through `EnvDestinationStore.setDestination`, and the secret only through the broker's persistence (`mcp-sso` and `generate-env`: the provider `getProvider` builds, every collaborator stated by the CLI; `mcp-auth`: the token API with its own provider factory) — never a means field or the client secret in a session write. The one exception is `mcp-sso … --cookie` (`saml` / `none`), whose handed-over cookies the CLI writes with the library's `bindingOf(means)` — the binding is computed in one place, the library's `src/bindingOf.ts` (`destinationBinding`, which `getProvider` and `persist` use); no canonicalising code lives in the CLI. Every command (and `generate-env`) works on a copy in a private temporary directory and replaces its output only after `flush()`. `broker.flush()` runs before the output is copied; a failure exits 1 and writes nothing. `--authn-request-id` is refused (no means field carries it).
```bash
mcp-auth --service-key ./key.json --output ./mcp.env --type xsuaa
mcp-auth --service-key ./key.json --output ./abap.env --type abap --credential
```

## Testing

Tests live in each package's `src/__tests__/` (see `docs/development/TESTING.md`):
- Library: `AuthBroker.test.ts` (the token API with a consumer provider — the carried-over 3.x suite, and one case on auth-stores 3's real `EnvDestinationStore` + `AbapSessionStore` files), `tokenApiShared.test.ts` (the token API on `getProvider`'s provider), `connection10.test.ts` (end to end: an `AdtCloudConnector` from `getProvider` against a local 401-then-200 server and token endpoint, the renewed token in the session file, then answered by `getToken`), `getProvider.test.ts`, `getProviderTokens.test.ts`, `getProviderBinding.test.ts` and `getProviderOidcSaml.test.ts` need nothing (stores are in-memory fakes of the contract, providers real; the SNC case writes a header-only library fixture of the host's architecture to a temp directory; the token grants talk to a token endpoint the test starts on 127.0.0.1, `helpers/tokenEndpoint.ts` — which also serves OIDC discovery and device authorization — and log in through a recording strategy or presenter; the SAML grants validate assertions from `@mcp-abap-adt/auth-mocks`' identity provider, one signing the Response, one the Assertion; the write retry runs under Jest's fake timers); `AuthBroker.integration.test.ts` reads real service keys and sessions only when `packages/auth-broker/tests/test-config.yaml` exists (from the template beside it) — without it every case returns at once.
- Library, client authentication (4.1.0): `clientAuthentication.test.ts` (the factories and the guard's fixed words, lazy reads, no key material anywhere), `clientAuthenticationRows.test.ts` (every client row with and without a strategy), `clientAuthenticationBinding.test.ts` (the strategy path's binding), `tokenProviderFactory.test.ts` (the fourth argument, bound secrets only, the grant refusal) — fake stores and auth-stores 3.3, certificate fixtures under `src/__tests__/fixtures/certificates/` (test-only, trusted by nothing).
- Library, live x509: `src/__tests__/live/x509.live.test.ts`, run only by `npm run test:live:x509` (`tests/live/x509/run.sh`: build, `setup.sh`, the suite, `teardown.sh` also on failure). It refuses unless `cf target` equals `XSUAA_CF_API` / `XSUAA_CF_ORG` / `XSUAA_CF_SPACE` exactly, and touches only what `setup.sh` recorded with its GUID in the ledger `tests/live/x509/.local/owned` (gitignored; the key and PEM files owner-only, never printed): an `xsuaa`/`application` instance (`credential-types: ["binding-secret","x509"]`) and a key made with `{"credential-type":"x509"}` each run. Cases: the key's shape; (a) broker + `fromServiceKeyCertificate()`; (b) `mcp-auth --credential --client-auth certificate`; (c) `generate-env --client-auth certificate`; (d) a failing run leaves the destination untouched, no PEM. Measured on a BTP trial 2026-10-05, all passed. Not in `npm test`, not in CI.
- Library, live: `src/__tests__/live/getProvider.live.test.ts`, run only by `npm run test:live` (`jest.live.config.js`; `jest.config.js` ignores `__tests__/live/`). `basic` over HTTP and RFC, `snc` over RFC, and `jwt`/`authorization_code` over HTTP (a seeded JWT the system refuses → 401 → renewal in `rejected()` → the new token in a temp copy of the session file; its `authorization` refuses, so no browser) through connection 10; each case reads only the `AUTH_BROKER_LIVE_*` variables it names and skips with the reason on stderr where they, the platform (SNC: Windows/macOS) or the RFC addon are missing — no configuration file. It reads the means with auth-stores 3's `EnvDestinationStore` (`AUTH_BROKER_LIVE_KEYS_DIR`) — the `jwt` case with its `AbapServiceKeyStore` over the SAP service keys (`AUTH_BROKER_LIVE_SERVICE_KEYS_DIR`), the grant stated by its 3.1.0 `grantType` option, the session's binding written back with the refused token — auth-stores 3.2, the library's dev dependency.
- **The broker stand** (`packages/auth-broker/tests/stand/`; `npm run test:stand` — root or package — starts it, runs `src/__tests__/stand/` and stops it, and CI runs the same as its own job, `broker-stand` in `.github/workflows/ci.yml`) runs Cloud Foundry UAA and Keycloak in Docker: real token endpoints for the token grants `getProvider` builds. It is auth-providers' `tests/stand` copied whole and owned here, so the broker's tests never depend on another repository: compose, `up.sh`/`run.sh`/`down.sh`, the UAA configuration, the Keycloak `test` realm and the test SAML IdP's key — committed fixtures, not secrets, trusted by nothing but the local stand, so a clone needs only Docker. Its compose project and containers are named `auth-broker-*`, so Docker tells it from auth-providers' stand; they share the default ports 8080/8081. `src/__tests__/stand/formLogin.ts` plays the user on UAA's login form and `/passcode` page and on Keycloak's login, device and consent pages — never a browser. Each suite composes auth-stores 3's `EnvDestinationStore` (means) and `AbapSessionStore` (secret) in temp directories and reads the session file back; it takes UAA's issuer from discovery, never from `UAA_URL`. Each runs only when its `UAA_URL` / `KEYCLOAK_URL` are set and otherwise skips, printing why. A server already running (from `npm run stand:up`) is left running; `run.sh` removes only what it started, per service. `uaaGrants`: `client_credentials`, `authorization_code`, `passcode`, each asserting `SAP_ISSUED_FOR` / `SAP_ISSUED_BY` in the session file, and a session bound to another URL not reused. `oidcGrants` (Keycloak): `password`, `oidc_authorization_code`, `device_code`, `token_exchange` — persisted with the binding, renewed after a 401. `samlGrants`: Keycloak is the IdP and UAA the SP — `saml2_pure` turns Keycloak's assertion into a real UAA session cookie through the test's `samlCookies` (posted to UAA's web SSO ACS), written as cookies, reused, renewed by a new login; `saml2_bearer` exchanges it at UAA's bearer grant. Both SAML logins are IdP-initiated (UAA 79 refuses an `InResponseTo` it did not send, at web SSO too), and the suite sets Keycloak's `uaa-sp` ACS and a one-hour assertion lifespan at run time (the default one minute is inside a provider's one-minute margin). It does not prove SAP ICF's SAML, nor tell the two validators apart (Keycloak signs both elements; the unit suite does).
- CLI: `mcpSsoConfig`, `mcpSsoSamlProviders`, `samlMetadata`, `runMcpAuth`, `runMcpSso`, `generateEnv` — need nothing: the runs go in-process against a local token endpoint (`src/__tests__/helpers/localServer.ts`) in temporary directories, with test doubles for every interactive step. The Keycloak and CAP stands under `packages/auth-broker-cli/tests/` are interactive, by hand only.
- Tests run sequentially (`maxWorkers: 1`) to ensure proper file state.

## Plans and Specs

Working documents (goals, specs, plans) under `docs/superpowers/` are kept in the tree only while active — i.e. not yet implemented and not cancelled. Once one has been fully implemented OR cancelled, delete it, at the latest before the release that ships the work; what it still owes the future goes into that PR's description first. History lives in git; the directory exists only while it holds work in progress (none since 4.0.0).
